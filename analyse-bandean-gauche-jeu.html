2. Analyse Détaillée de l'Onglet "Jeu"

2.1 Architecture du composant

GameTab.tsx — 390 lignes

  • 3 sections : Phase Actuelle, Ordre d'Appel, Autres entités
  • Logique métier mêlée au rendu (useMemo, handlers inline)
  • 2 states locaux : expandedCalledTags, expandedOtherTags
  • 2 handlers principaux : handleModifyTagField, handleModifyMarkerTagField
  • 1 useMemo complexe : calcul de calledEntities et otherEntities

2.2 Points positifs +

  • useMemo pour calledEntities / otherEntities — bon pour les performances
  • Distinction jour/nuit avec icônes adaptées (Moon/Sun/FastForward)
  • Compteurs +/- pour uses, lives, votes, points fonctionnels
  • Auto-delete quand uses = 0 géré avec cascade sur les enfants
  • Gestion séparée Players vs Markers
  • Filtrage via showInGameTab

2.3 Problèmes identifiés −

P1. Code dupliqué massif (lignes 206-294 et 338-377)

Les compteurs +/- pour Player et Marker sont copiés-collés 2 fois avec des tailles différentes :

  • Player : text-[10px], w-4 h-4, w-4 pour le span
  • Marker : text-[9px], w-3.5 h-3.5, w-3 pour le span

Impact : ~80 lignes dupliquées, maintenance difficile, risque de divergence

Solution : Composant réutilisable TagFieldControls

P2. Pas de sections pliables

Contrairement aux autres onglets (PlayersTab, RolesTab, TagsTab) qui utilisent SortableSection avec collapse/expand, le GameTab affiche tout en permanence.

Impact : Avec 10+ joueurs, le panneau devient illisible et nécessite beaucoup de scroll

Solution : Implémenter le pattern SortableSection existant

P3. Pas de recherche/filtrage

Aucun moyen de filtrer un joueur spécifique dans l'ordre d'appel ou les autres entités.

Impact : Perte de temps pour trouver un joueur spécifique

P4. Boutons +/- trop petits

w-4 h-4 (16px) avec text-[10px] : difficilement cliquables, surtout sur écran tactile.

Recommandation : Minimum w-6 h-6 (24px) pour l'accessibilité

P5. Manque de feedback visuel

  • Pas d'indicateur quand un compteur atteint 0
  • Pas de confirmation avant suppression auto
  • Pas de toast/notification sur les changements
  • Pas de barre de progression pour uses/lives

P6. Ordre d'appel statique

Pas de drag-and-drop pour réorganiser l'ordre d'appel manuellement.

Impact : Le MJ ne peut pas ajuster l'ordre en temps réel

P7. Section "Autres entités" limitée

max-h-40 (160px) : trop petit si beaucoup de joueurs non-appelés.

Recommandation : max-h-60 ou scrollable avec hauteur dynamique

P8. Pas de mode "Focus"

Pendant une partie, le MJ voudrait ne voir que le joueur actuellement appelé, pas toute la liste.

Solution : Bouton "Focus" pour isoler le joueur en cours

3. Suggestions d'Amélioration

3.1 Design

  1. Header avec résumé : afficher un compteur global (ex: "3 appelés / 8 joueurs")
  2. Cartes joueur avec couleur d'équipe/rôle : bordure colorée comme dans PlayersTab
  3. Icônes visuelles pour chaque tag (comme TagsTab avec icon)
  4. Mode "Focus phase" : bouton pour isoler le joueur en cours d'appel
  5. Barre de progression pour les uses/lives (ex: 2/5 avec une barre)
  6. Pastilles de statut : mort, dort, aveuglé visibles directement

3.2 UX

  1. Sections pliables : aligner avec le pattern SortableSection des autres onglets
  2. Recherche rapide : input pour filtrer par nom de joueur
  3. Compteurs cliquables : augmenter la taille à w-6 h-6 minimum
  4. Raccourcis clavier : Space = phase suivante, R = reset
  5. Mode "appel en cours" : highlight du joueur actif avec animation subtile
  6. Historique des phases : voir les phases précédentes

3.3 Architecture

  1. Extraire TagFieldControls : composant réutilisable pour les compteurs
  2. Extraire CallOrderCard : carte pour chaque entité appelée
  3. Extraire PhaseControl : section phase actuelle
  4. Hook personnalisé useCallOrder() pour la logique de tri
  5. Virtualisation si > 20 joueurs (déjà présent : VirtualList.tsx)

3.4 Fonctionnalités manquantes

  1. Export de l'ordre d'appel (copier dans le presse-papier)
  2. Timer par phase intégré (le timer existe mais pas lié au GameTab)
  3. Notes rapides par joueur pendant la phase
  4. Marquer un joueur comme "traité" dans l'ordre d'appel
  5. Vue chronologique : historique des appels passés

5. Détails Techniques — Implémentation P0

5.1 Composant TagFieldControls

Props attendues

interface TagFieldControlsProps {
  tag: TagInstance | Marker['tag'];
  entity: Player | Marker;
  entityType: 'player' | 'marker';
  size?: 'sm' | 'md';
}

Responsabilités

  • Afficher les 4 champs conditionnels (uses, lives, votes, points)
  • Gérer les boutons +/- avec les bonnes tailles
  • Afficher "Illimité" pour votes = -1
  • Cacher les boutons si votes = -1

5.2 Sections pliables avec SortableSection

Structure proposée

  • Section 1 : "Phase Actuelle" — contrôles jour/nuit/tour
  • Section 2 : "Ordre d'Appel" — entités appelées avec compteurs
  • Section 3 : "Autres Entités" — joueurs/marqueurs non appelés

Pattern à réutiliser

Le composant SortableSection existe déjà dans PlayersTab, RolesTab et TagsTab. Il faut :

  1. Extraire SortableSection dans un fichier partagé ou le dupliquer dans GameTab
  2. Ajouter les states openSections et sectionOrder
  3. Envelopper dans DndContext + SortableContext
