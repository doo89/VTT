1. Connexion avec Supabase

1.1 Fichier principal : src/lib/supabase.ts

Le client Supabase est initialisé avec un système de cascade de priorités pour résoudre les credentials (URL et clé anon).

1.2 Cascade de résolution des credentials

Priorité Source Clés Description
1 Paramètres URL ?sburl= / ?sbkey= Base64 encodés, stockés en sessionStorage
2 sessionStorage VTT_SB_URL_OVERRIDE Persiste pendant la session du navigateur
3 localStorage VTT_SUPABASE_URL Persiste entre les sessions
4 Variables d'environnement VITE_SUPABASE_URL Fallback défini dans .env

1.3 Logique d'initialisation

const supabaseUrl = getEnvUrl() as string;
const supabaseAnonKey = getEnvKey() as string;

let sbClient = null;
if (supabaseUrl && supabaseAnonKey && supabaseUrl.startsWith('http')) {
  sbClient = createClient(supabaseUrl, supabaseAnonKey);
}

// Le client peut être null (permet le dev local sans Supabase)
export const supabase = sbClient;

1.4 Fonctions utilitaires

  • uploadFileToStorage(file: File) → Upload vers le bucket images-all, retourne l'URL publique
  • deleteFileFromStorage(fileUrl: string) → Supprime un fichier du bucket via son URL publique

1.5 Types exportés

  • SyncStatePayload → Structure complète de l'état broadcasté (players, roles, teams, tags, handouts, wiki, room, logs, etc.)
  • JoinRequestPayload → Payload de demande de connexion (playerName)

2. Utilisation du fichier .env.example

2.1 Contenu

# .env.example
VITE_SUPABASE_URL=https://qxtnkhwjvhorvadjwmfh.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_lyk52r8Cy5Y_F8K14Orw_51yurkaD

2.2 Rôle

  • Fournit les credentials par défaut pour Supabase
  • Utilisé comme dernier fallback dans la cascade de getEnvUrl() / getEnvKey()
  • Le préfixe VITE_ est requis pour que Vite expose ces variables au client via import.meta.env
Important : Le fichier .env.example sert de template. En production ou en local, il faut créer un fichier .env (non versionné) avec ses propres credentials Supabase.

2.3 Fichiers .env.example trouvés

  • .env.example → Racine du projet (principal)
  • public/.env.example → Probablement redondant ou pour un autre usage

3. Synchronisation des données MJ ↔ Smartphone

3.1 Architecture générale

Le système utilise une architecture Hub-and-Spoke via Supabase Realtime. Le MJ est le hub central, les smartphones sont des clients connectés au même canal.

+-----------------+ | Supabase | | Realtime | | Channel | +--------+--------+ | +----------------+----------------+ | | | v v v +---------+ +--------+ +--------+ | MJ | | Joueur | | Joueur | | (Host) | | 1 | | 2 | +---------+ +--------+ +--------+

3.2 Canaux de communication

Élément Canal Supabase Clé de présence
MJ (Host) room:{roomCode} 'host'
Smartphone (Player) room:{roomId} playerName

3.3 Côté MJ (Host)

Fichier : src/lib/realtime-host.ts

Initialisation

  • setupHostRealtimeSubscription() s'abonne au store Zustand
  • Dès qu'un roomCode est généré, initHostRealtime(code) crée le canal
  • Le canal est configuré avec broadcast: { self: false, ack: false } pour optimiser les performances

Broadcast de l'état

Chaque changement du store déclenche un broadcast :

  • Full sync sync_state → État complet envoyé au premier chargement ou quand le diff est trop volumineux
  • Diff sync sync_state_diff → Uniquement les champs modifiés (optimisé via state-diff.ts)

Mécanismes de contrôle du débit :

  • Debounce : 150ms après le dernier changement avant broadcast
  • Throttle positions : pan/zoom limité à 2 broadcasts/seconde (500ms)
  • Seuil payload : si le diff excède 200KB, fallback vers un full broadcast

Écoute des événements clients

Le MJ écoute et traite les événements suivants :

  • join_request → Ajoute le joueur automatiquement (room publique) ou met en file d'attente (room privée)
  • get_state → Force un broadcast immédiat de l'état complet
  • smartphone_action → Traite les actions complexes des tags (sélection de joueurs, fusion de tags, feedback, révélation d'info, vérification de rôle, etc.)
  • poll_response → Enregistre la réponse d'un joueur à un sondage
  • group_vote_response → Enregistre un vote dans un vote de groupe
  • close_group_vote → Calcule les résultats et assigne le tag au gagnant
  • soundboard_action → Déclenche un son à distance (vérification du passcode)
  • checklist_action → Coche/décoche un item de checklist à distance
  • action_trigger → Exécute une action à distance
  • remote_player_update → Met à jour les notes privées d'un joueur

3.4 Côté Smartphone (Player)

Fichier : src/pages/PlayerView.tsx

Connexion

  • Rejoint le canal room:{roomId} avec presence: { key: playerName }
  • Utilise matchedPlayerIdRef (ref) pour résister aux renommages par le MJ

Réception du state (sync_state)

  • Trouve le joueur par ID (priorité) ou par nom normalisé (accents supprimés, lowercase)
  • Stocke matchedPlayerIdRef.current pour les mises à jour futures
  • Envoie channel.track({ playerId, name }) pour la présence
  • Met à jour tous les state locaux : rôle, équipe, tags, handouts, wiki, logs, custom popups, votes, countdown, timer

Actions joueur

handleSmartphoneAction() envoie un événement smartphone_action au MJ avec :

  • playerName et playerId
  • tagInstanceId → Le tag concerné
  • feedbackMessage → Message à afficher au MJ
  • selectedPlayerIds → Joueurs sélectionnés (pour les sélecteurs)
  • smartphoneReturnInfo → Type d'info à révéler (role, team, seen_role, seen_team)
  • autoDeleteSmartphoneUI → Supprimer le tag après utilisation

3.5 Flow de connexion d'un joueur

Smartphone MJ (Host) | | | 1. Rejoint canal room:{code} | |---------------------------------->| | | | 2. join_request { playerName } | |---------------------------------->| | | | 3. get_state | |---------------------------------->| | | | 4. sync_state (full) | |<----------------------------------| | | | 5. Trouve joueur par nom/ID | | matchedPlayerIdRef = found.id | | | | 6. track({ playerId, name }) | |---------------------------------->| | | | 7. Retry toutes les 4s si | | pas matché jusqu'à succès | |---------------------------------->|

3.6 Événements échangés

Événement Direction Description

get_state Player → Host Demande l'état complet du jeu
sync_state Host → Player Broadcast de l'état complet
sync_state_diff Host → Player Broadcast incrémental (diff uniquement)
smartphone_action Player → Host Action d'un tag (sélection, fusion, feedback)
feedback_popup Host → Player Message de feedback à afficher au joueur
poll_response Player → Host Réponse à un sondage
group_vote_response Player → Host Vote dans un vote de groupe

3.7 Optimisations

Diff-based broadcast (src/lib/utils/state-diff.ts)

  • Compare l'état précédent avec le nouveau via computeStateDiff()
  • N'envoie que les champs qui ont changé (définis dans BROADCAST_FIELDS)
  • Merge côté client via mergeStateDiff()

Image stripping

  • Les images en data URI ou supérieures à 2000 caractères sont remplacées par null dans les broadcasts
  • Évite de saturer le canal avec des payloads trop lourds

Champs broadcastés

export const BROADCAST_FIELDS = [
  'players', 'roles', 'teams', 'tags',
  'handouts', 'isNight', 'cycleMode',
  'isPublicMode', 'displaySettings',
  'wiki', 'checklist', 'customPopups',
  'activeCustomPopupId', 'activeGroupVote',
  'smartphoneCountdown', 'timer',
  'logs', 'room',
];

Présence

  • Le MJ suit les joueurs connectés via Supabase Presence
  • isHostOnline est détecté côté smartphone
  • Les joueurs sont trackés par playerId une fois matchés

4. Store Zustand

Fichier : src/store/index.ts

4.1 Configuration

  • State management : Zustand avec middleware persist (localStorage)
  • Undo/Redo : Middleware zundo (temporal) avec limite de 50 états
  • Sélecteurs optimisés : Exportés depuis src/store/selectors.ts

4.2 Persistance

Le store est persisté dans localStorage sous la clé vtt-storage. Certains états transitoires sont exclus de la persistance :

  • editingEntity
  • actionCreatorState (et sous-états)
  • pendingActionConditions / pendingActionEffects
  • tagDistributorState
  • magneticPoints / showMagneticPoints
  • checklistState
  • activeCustomPopupId

4.3 Rehydratation

Au rechargement de la page, le store est rehydraté depuis localStorage et les états transitoires sont réinitialisés :

onRehydrateStorage: () => (state) => {
  if (state) {
    state.editingEntity = null;
    state.actionCreatorState.isOpen = false;
    state.pendingActionConditions = [];
    state.pendingActionEffects = [];
  }
}
